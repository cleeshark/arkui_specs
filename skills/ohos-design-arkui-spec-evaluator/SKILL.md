# ArkUI Function Spec/Design Evaluator

Evaluate one complete ArkUI Function without changing the evaluated artifacts. The evaluator explains evidence-backed defects; deterministic structure, path, traceability, link, and SDK declaration existence checks remain owned by `specs/tools/spec_eval/`.

## Authority and boundaries

Use these sources in descending authority:

1. Frozen public SDK declarations for external API surface and signatures.
2. Frozen ace_engine, adapter, related-repository source, build files, and tests for implemented behavior.
3. Function Registry, Feature Registry, all non-Deprecated Feature specs, and shared `design.md`.
4. Static findings and evidence bundles generated by `spec_eval`.
5. Confirmed Pilot Review only as a calibration reference, never as evidence that replaces source verification.

Keep these boundaries throughout the run:

- Evaluate the whole FuncID, not a selected Markdown file or a single Feat.
- Do not modify Spec, Design, Registry, generated site files, or confirmed Review files.
- Do not use author, organization, generating model, document length, table count, diagram count, citation count, or checked self-audit boxes as quality signals.
- Do not remove static findings, lower their gate, or duplicate deterministic format findings as new semantic findings.
- Treat missing evidence as `NOT_VERIFIABLE`; do not convert inference into implementation fact.
- NEXT-007 produces `semantic-result.json`. Published score, admission level, site report, and formal aggregation belong to NEXT-008/009.

During a blind evaluation, do not read confirmed Reviews or previous automatic runs until the new
`semantic-result.json` passes protocol validation. Before that freeze point, forbid access to
`specs/evaluation/reviews/**` and historical directories under `specs/.evaluator/next-007/**`.
For broad searches, add explicit exclusion globs for both trees; read only the exact current run
path when it is stored below `next-007`. Use confirmed Reviews only after freezing the result and
only when the user requests calibration.

## Required inputs

Require all of the following before judging:

- A concrete `FuncID`.
- A complete Function evaluation directory produced by `spec_eval evidence`.
- Frozen `specs/evaluation/rubric.yaml`, complexity rules, design completeness rules, and semantic result Schema.
- Read access to every source revision and related SDK repository named by the evidence.

Read [`references/input-output-contract.md`](references/input-output-contract.md) completely before preparing a run. Read [`references/criterion-guide.md`](references/criterion-guide.md) completely before assigning conclusions.

## Workflow

### 1. Validate the frozen protocol

From the ace_engine repository root, run:

```bash
PYTHONPATH=specs/tools python3 -m spec_eval.protocol_validator \
  --evaluation-root specs/evaluation
```

Stop if Rubric v0.3 is not `frozen`, protocol versions disagree, or the protocol validator reports any error.

### 2. Generate the complete Function evidence package

Use a temporary or explicitly selected output directory:

```bash
python3 specs/tools/spec_eval/cli.py \
  --output /tmp/spec-evaluation \
  evidence --func-id <FuncID>
```

Exit code `1` means the Function has deterministic quality findings but the report was generated. A missing output directory, incomplete Function, tool exception, or exit code for tool failure blocks semantic evaluation.

Require these artifacts under `<output>/<source-revision>/<FuncID>/`:

- `function-context.json`
- `static-result.json`
- `evidence-manifest.json`
- every shard declared under `evidence/`
- `report.md` for human navigation

### 3. Create a run-local semantic template

NEXT-007 calibration starts with the 12 frozen Pilot Functions. Create a result outside `evaluation/reviews/`:

```bash
python3 specs/skills/ohos-design-arkui-spec-evaluator/scripts/create_pilot_template.py \
  --func-id <FuncID> \
  --input-dir /tmp/spec-evaluation/<source-revision>/<FuncID> \
  --run-id <unique-run-id> \
  --output /tmp/spec-evaluator/<FuncID>/<unique-run-id>/semantic-result.json
```

The helper rejects non-Pilot FuncIDs, mismatched revisions, incomplete evidence shards, tool-error static results, and attempts to write into confirmed Review storage. General registered-Function template generation is intentionally deferred until Pilot calibration is stable.

### 4. Review deterministic signals first

Read `function-context.json`, `static-result.json`, `evidence-manifest.json`, `report.md`, and all evidence shards before opening additional source files.

For each static finding:

- Preserve its rule ID, severity, and gate authority.
- Use it as an input signal for the matching hybrid Criterion.
- Add a semantic finding only when evidence establishes a separate semantic defect, such as an unsupported behavior claim or incomplete design decision.

### 5. Evaluate all 20 Criteria in Rubric order

Follow the exact Criterion order from `rubric.yaml`. Do not skip a Criterion or reorder the output.

Before assigning conclusions, create a run-local scratch coverage matrix:

- Correctness: one row for every AC and Rule claim. Split compound statements into independently
  checked facets, including condition, input, quantitative relation, terminology, direction/axis,
  state transition, and observable result.
- AC testability: for every boundary or versioned AC, record the concrete trigger values/branch and
  the exact result assertion. A test name or nearby generic test does not prove boundary coverage.
- Reset/default/update semantics: cross every applicable frontend or entry path with configuration
  gates/API versions, prior state, input class, post-state fields, and observable output. Do not
  generalize one supported reset path to other frontends or pre-existing states.
- Design runtime: every non-Deprecated Feat crossed with input/entry, state update, core processing,
  output/event, exception/recovery, and test handoff.
- Design completeness: one row for every applicable `required_check` in the frozen rules.
- Compatibility: one row for every included device, API version, frontend, and platform identified
  by the Function context and Pilot evaluation scope.

An included device form makes `COMPATIBILITY-MULTI-DEVICE` applicable. Absence of a dedicated
device test is not by itself a defect when frozen source proves that the included forms share the
same generic constraint, density, theme, and rendering path and no device-specific branch exists.

Do not finish a Criterion while an applicable matrix row remains unreviewed. The scratch matrix is
run-local working state and does not create a separately maintained capability baseline.

For every Criterion:

1. Establish applicability from Function complexity, registered Feats, API exposure, implementation layers, and actual system impact.
2. Enumerate the required claim scope: all relevant ACs/Rules, all non-Deprecated Feats, or the whole Function as specified by the Rubric.
3. Verify claims against source, SDK, tests, Registry, Spec, Design, and static evidence as applicable.
4. Assign a conclusion to every applicable unit before aggregating the Criterion.
5. Aggregate exactly one Criterion conclusion: `SUPPORTED`, `PARTIALLY_SUPPORTED`, `CONTRADICTED`, `MISSING`, `NOT_APPLICABLE`, or `NOT_VERIFIABLE`.
6. Record concise reasoning, reproducible evidence, and evidence-backed findings.

Emit one Finding for each independently actionable defect. A Criterion may therefore contain
multiple Findings with the same aggregate conclusion and severity. Do not merge unrelated AC,
frontend, version, state, build, or verification defects merely to keep one Finding per Criterion.

`SUPPORTED` means every applicable unit in the Criterion scope is covered and verified. A strong example does not compensate for an omitted Feat, AC, branch, platform, or lifecycle path.
Use `PARTIALLY_SUPPORTED` when the Criterion's main body is present and supported but one or more
units are incomplete, inaccurate, or locally contradicted. Use `CONTRADICTED` only when the core
capability, primary architecture direction, or Criterion-wide claim conflicts with frozen evidence.
Use `MISSING` only when the Rubric outcome policy defines the required content or covered unit as
absent; do not promote one missing subcheck inside an otherwise present unit to Criterion-wide
`MISSING`. Derive Finding conclusion and minimum severity from the final aggregate Criterion result,
not from the harshest local observation.
Always apply a Criterion's frozen `outcome_policy` before these general aggregation heuristics. If
the policy explicitly classifies a present-but-placeholder section as `MISSING`, do not soften it to
`PARTIALLY_SUPPORTED` merely because the heading or a generic statement exists.
For `DESIGN-VERIFICATION-PLAN`, do not infer `MISSING` from absent target/binary/filter details
alone. Function-specific unit-test, manual, Feat/AC, boundary, or risk validation directions establish
that a plan body exists; missing execution details then aggregate to `PARTIALLY_SUPPORTED`.
Use `MISSING` only when no Function-specific verification direction or usable scenario exists.

### 6. Apply Function modeling without a separate capability baseline

For `FUNCTION-FEAT-COVERAGE`, `FUNCTION-FEAT-DECOMPOSITION`, and `FUNCTION-FEAT-BOUNDARY`, derive the currently visible capability surface from Registry, Feature specs, shared Design, source entry points, public/internal API declarations, build registration, and tests.

- Coverage: every discovered functional entry and key behavior has a Feat owner.
- Decomposition: each Feat is cohesive, independently verifiable, and not an oversized mixed capability or a trivial document fragment.
- Boundary: Feat responsibilities do not overlap ambiguously; shared mechanisms and cross-Feat dependencies have explicit ownership.

Judge coverage by ownership of independently observable and independently acceptable capability.
Internal bridges, frontend dispatch paths, generated modifiers, shared libraries, build artifacts,
and legacy implementations do not become separate capabilities merely because Design omits their
details. When a broad component Feat clearly owns their observable behavior, keep coverage
`SUPPORTED` and score missing implementation detail under the applicable Spec scope or Design
Criterion. Use `PARTIALLY_SUPPORTED` only when an actual functional entry, key behavior, or
lifecycle capability has no Feat owner or is explicitly outside every Feat's scope.

Do not introduce or require a separately maintained capability checklist.

### 7. Complete and validate the semantic result

Update coverage counters and set `execution.semantic_complete` to `true` only after all 20 Criteria have been judged. Keep it `false` when required evidence or a required repository is unavailable.

Validate the result:

```bash
python3 specs/skills/ohos-design-arkui-spec-evaluator/scripts/validate_semantic_result.py \
  /tmp/spec-evaluator/<FuncID>/<unique-run-id>/semantic-result.json
```

Repair every protocol or Schema error before delivery.

### 8. Deliver without overwriting the baseline

Return:

- The path to `semantic-result.json`.
- Criterion-level findings grouped by severity.
- Missing evidence and blocked Criteria.
- A statement that official Review, Spec, Design, and Registry files were not modified.

When the user explicitly requests calibration, compare the run with `specs/evaluation/reviews/<FuncID>.yaml` by Criterion, finding substance, severity, and total deduction. Never automatically rewrite the confirmed Review.

## Conclusion discipline

- `SUPPORTED`: all applicable scope is verified and no defect remains for the Criterion.
- `PARTIALLY_SUPPORTED`: the main content exists, but at least one applicable unit is incomplete, inaccurate, or locally contradicted.
- `CONTRADICTED`: the Criterion's core capability, primary architecture direction, or overall claim conflicts with frozen implementation or contract evidence.
- `MISSING`: the Rubric-defined required content or required covered unit is absent.
- `NOT_APPLICABLE`: the Rubric allows N/A for this Criterion and reproducible evidence proves it does not apply.
- `NOT_VERIFIABLE`: evidence is missing, unavailable, stale, ambiguous, or insufficient to make a defensible judgment.

Critical and Major findings need at least one reproducible evidence item containing path, frozen source revision, content hash, reason, and recommendation. Source line numbers are useful when stable but are not mandatory.

## Stop conditions

Stop and report the blocking evidence instead of guessing when:

- Function context, static result, evidence manifest, or a declared evidence shard is missing.
- FuncID or source revision differs across input artifacts.
- Required ace_engine, SDK, NDK, ArkUI-X, or related-repository source is not available.
- Rubric, complexity, design completeness, evaluator protocol, or Schema versions disagree.
- The requested FuncID is outside the frozen Pilot during the NEXT-007 MVP framework stage.
